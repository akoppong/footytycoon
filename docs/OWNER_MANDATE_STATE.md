# E02: saved mandate state and read contract

This unit implements the persistence and immutable read contract from [E00 amendment A1](OWNER_MANDATE_EXPERIMENT.md), without changing selection, recommendation ranking, owner command execution or UI. It is based on reviewed E01B revision `ca9614c65b3bc5d445d07c91be1a0946c9608e99` ([PR #48](https://github.com/akoppong/footytycoon/pull/48)), which includes E01 `5a72b351479c69d06b76179f59d2425eb478722e` and E00/A1 integration `df54a03fd4cd47786cb771f200bff8904dc98ac1`. The selected branch is `codex/owner-mandate-state`; PRs remain open for owner review. E01B's reproducible schema-23 starts for seeds 2026 and 2030 meet the entry gate; 2026 remains primary. See the [checkpoint manifest and loading instructions](OWNER_MANDATE_BASELINE.md#e01b-results-and-checkpoint-manifest).

## Schema and migration

The next sequential schema is **24**, simulation version `owner-mandates-24`; content and random versions are unchanged. New worlds have `MandateState.Default`: manager `Readiness`, director `CurrentRecommendation`, revision 0. All three new history/evidence lists start empty.

The existing decode chain still imports every previously supported schema. Its new 23→24 step validates the schema-23 aggregate, initializes only the new state/lists, then validates schema 24. It does not regenerate old forecasts, receipts, approvals, match results, people, commitments, cash, ledger entries or random streams. An old pending offer remains an old pending offer; no mandate origin is invented. Loading through `GameSession` retains the existing source-preserving vault/fork rules.

Encoded bytes necessarily change because the schema and new fields change. Newly generated forecast/proposal hashes can therefore change. Stored identifiers in imported history remain exact; new identifiers must be compared with a consistent mapping of their references, not discarded wholesale. Defaults do not select different players, change recommendations, alter owner approvals or consume random draws.

## Exact shared types

All new Core types are in `OwnerMandates.cs`. Records are immutable; their collections use `ImmutableArray<T>`. The World owns mutable lists only inside the existing serialized aggregate/application worker.

| Transition | `MandateChange(CommandId, Week, WorldRevision, Before, After)` in `World.MandateHistory` | E05 appends once |

`MandateProposal.Command` supplies both target modes and expected world revision; `Before` supplies both old modes/revision. `WorldFingerprint` binds the quote to the world, not merely its revision. The pending commitment strings and explanatory effect are preview data, not saved spending authority. These data records do not implement a command handler: E05 must still provide no-op rejection, confirmation/idempotency, stale fingerprint checks and durable publication.

`DecisionWorldRevision` is captured when the pure selection/recommendation is computed, before its publication. It disambiguates multiple changes in one week and is separate from the mandate revision. A selection's week comes from its fixture; a recommendation carries its decision week explicitly. E06 must capture the decision's real revision rather than substituting the post-commit/post-advance revision.

Approach `Outcome` reuses the existing `ApproachOutcome` enum (`Pending`, `Signed`, `Declined`, `Unavailable`, `ChecksFailed`), but saved resolution evidence rejects `Pending`. `Reason` retains the first actual binding failure or acceptance explanation in E00's existing-check order; E06 must populate it from execution rather than guessing from the later world. This unit does not execute those checks or manufacture outcomes. A signed record links its original contract and wage obligation; a closed record has neither.

## Invariants and downstream writing rules

- Current enum values and nonnegative revisions are validated. Mandate history starts from defaults, has contiguous mandate revisions and coherent old/new states, increasing world revisions, nondecreasing weeks and no no-op transition. Each change links the matching receipt in `World.Commands`. Do not add a second receipt map or append mandate changes to investment `World.History`: the latter would change bid IDs and acceptance streams.
- Every origin must match the latest transition at `DecisionWorldRevision`. Its revision/week must be possible relative to the history: a later world revision cannot belong to an earlier week than the recorded decision. Same-week order uses revisions. Revision 0 means explicit defaults; null means unknown legacy origin, not defaults.
- Selection evidence is unique per owned, resolved fixture. Its snapshots refer to retained known identities, not only today's squad. There are at most two distinct native-role outfield swaps; the displaced player is older than 23, the selected player at most 23, and the arithmetic sacrifice is 0–5. Selected players must appear in the actual native-role lineup and displaced players must not appear. Readiness cannot record swaps. These structural checks do not recreate historical ranking/availability; E03 tests exact selection and E06 captures actual facts.
- An approach is unique by original forecast ID and must resolve to one existing free-agent approval. Recommendation snapshots validate person/role/age/ability, integer wage dates/commitment arithmetic, reason/mode consistency and exact selected approved terms. A Value alternative preserves role, ability floor and both cost bounds; fallback/current evidence retains the same candidate. E04 still owns exact ranking and production previews.
- Resolution must retain the approval's origin, person and ordinary next-week timing, with no live bid remaining. Signed references must identify the retained owned wage obligation with matching original wage/start/end and contract description. Renewals/departures must not replace those links with the player's later contract. Closed outcomes cannot contain contract/obligation IDs.
- Empty lists and absent evidence are valid until E06 writes them. Legacy approval outcomes may have `Recommendation = null` and `Origin = null`; never create a synthetic recommendation or default origin for an old action. One approach record may begin with its recommendation and no outcome, then be replaced with an immutable copy containing its single outcome. Queries and quotes must not append history.

`MandateView` copies the World lists into immutable arrays and retains immutable nested records. `HistoricalMatches` contains every retained owned match, including those without mandate evidence, across the existing career limit. It does not expose World collections. This lets later UI resolve an earlier fixture after current-season `GameView.Results` becomes empty at rollover. Missing evidence remains absent and must not be inferred from current modes.

## Validation and limitations

The persistence tests construct records directly because E05 does not yet exist. Controlled fixtures establish validation/retention boundaries; they are not the playable human-study scenario. Tests cover current round trips and joint changes, invalid enums/history/receipt links, prospective legacy pending-bid import with source bytes preserved, selection/approach references and origin chronology, exact quote/outcome links, retention of original signed obligations through renewal or release, and pure immutable query/history access after rollover.
